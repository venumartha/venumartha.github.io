Incident tickets

Five systems from production, filed the way we actually track them. Each ticket is explorable: problem, constraints, architecture, decisions, trade-offs, lessons.

INC-AI-001· AI SYSTEM SHIPPED

Applied AI · Production RAG system

Giving clinical teams plain-English access to their own device data

AWS Bedrock, Titan Embeddings v2, Claude 3 Sonnet, pgvector, Elasticsearch

Clinical and ops teams needed engineers to answer basic questions about their own device data. Every question meant filing a ticket and waiting on someone with database access.

Healthcare data, so the whole pipeline had to stay inside the platform's existing AWS account boundary and security posture. The source data updates on a schedule, not once, so the index had to stay current, not just accurate on day one.

A scheduled Lambda indexer chunks operational data and embeds it with Titan v2 into pgvector on RDS Postgres. Elasticsearch runs alongside for hybrid keyword and semantic retrieval. On query, the question is embedded, matched by cosine similarity, and the retrieved context is passed to Claude 3 Sonnet to answer in plain English.

Chose Bedrock over a third-party LLM API specifically to keep the pipeline inside the account boundary the rest of the platform already operates under. Chose pgvector over standing up a dedicated vector database, since Postgres was already the operational store and it kept hybrid retrieval to one additional extension instead of one additional system to run and secure.

pgvector doesn't match a purpose-built vector database at very large scale, but at this corpus size it removed an entire system from the operating surface. Running Elasticsearch and pgvector together added a second retrieval path to maintain in exchange for better recall than either alone.

The prototype went from a Friday start to a working retrieval pipeline by Sunday, which worked because the retrieval problem was already well scoped, not because RAG itself is simple. The harder part was operational: keeping the index current on schedule and making the system honest when it doesn't know an answer.

INC-002· P0 CRITICAL RESOLVED

Distributed systems · Data integrity

Finding invisible data loss inside a third-party Kafka Connect sink

MSK, Kafka Connect, custom sink connector, mTLS, IAM auth

A production Kafka pipeline was silently losing data. Output looked valid, so no alarms fired. Underneath, a third-party MSK Kafka Connect sink had a replication lag bug that surfaced as a generic 504 timeout under load.

20,000+ connected medical devices across 1,500+ hospital locations feed this pipeline continuously. Downtime or silent loss has direct clinical impact, so any fix had to ship without a maintenance window. The root cause was inside a third-party connector, outside our own code.

Replaced the vendor sink with a custom Kafka Connect sink connector: S3-sourced plugin, IAM auth instead of static credentials, exponential backoff on retries, and PEM certificate normalization to eliminate mTLS handshake failures.

Rather than wait on the vendor to patch the replication bug on their own timeline, built and owned a custom connector so the fix and its testing were fully in house and verifiable.

Owning a custom connector means owning its maintenance going forward, in exchange for not depending on a vendor fix with no committed timeline for a system feeding clinical infrastructure.

The bug hid under a generic 504 for two weeks before the actual cause, a PEM normalization mismatch, surfaced. The lesson that stuck: read the actual wire format before trusting a library's abstraction of it.

INC-004· P1 HIGH RESOLVED

Platform engineering · Multi-tenant analytics

Self-serve dashboards for 500+ enterprise clients without a security model per client

QuickSight, cross-account IAM federation, CDK TypeScript

No embedded analytics capability existed. Every dashboard request from an enterprise client meant custom engineering work, one client at a time.

Enterprise clients are already isolated into separate AWS accounts for compliance reasons, so the platform had to respect that boundary rather than work around it.

A multi-account QuickSight embedding platform with cross-account IAM role federation, supporting both anonymous and user-based session modes, provisioned entirely through CDK TypeScript.

Chose cross-account IAM federation over duplicating dashboard infrastructure per client account, so one platform could serve every client inside their existing account boundary.

Federated IAM is harder to reason about and debug than a single-account setup, but it matched how the rest of the platform was already segmented for compliance, avoiding a second security model to maintain.

INC-003· P1 HIGH RESOLVED

Reliability · Observability

Cutting root-cause time from hours to minutes across every production service

CloudWatch RUM, Synthetics, severity-bucketed alerting

Engineers spent two to four hours log diving per incident. There was no unified observability layer and no synthetic monitors across production services.

Had to work across every production microservice without asking each team to instrument by hand, or adoption would stall out team by team.

A CloudWatch RUM and Synthetics canary platform adopted across all production microservices, with severity-bucketed alerting so on-call engineers see what matters first.

Standardized observability at the platform level rather than leaving instrumentation up to each team's own choices.

A standardized layer is less flexible than letting each team pick its own tools, but that consistency is what made a 20 minute MTTR achievable platform-wide instead of team by team.

ARCHIVE · VANGUARD· P1 HIGH RESOLVED · 2019–2022

Fintech · Reliability at scale

Root-causing three P1 incidents to one recurring pattern in a billion-dollar transaction platform

Java, Spring Boot, GraphQL, AppSync, Redis, ECS Fargate

A missing idempotency check caused a production incident processing millions of dollars in transactions. Two more P1 incidents followed later, on the surface unrelated.

Billions of dollars in transactions running through 1,500+ ECS Fargate tasks. Any fix had to ship without introducing new risk to a live financial platform under SOC 2 audit.

Java and Spring Boot microservices with circuit breakers and idempotency guards, a GraphQL API layer on AWS AppSync, and Redis caching in front of Postgres.

Instead of patching each P1 incident individually, traced all three across 12 services back to the same root pattern: missing idempotency or uncapped retry loops. Fixed the pattern once.

The postmortem discipline from the first incident, writing it down and fixing the root cause rather than the symptom, is what prevented the next two from recurring at all.
